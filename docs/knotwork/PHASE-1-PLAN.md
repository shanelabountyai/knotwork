# Knotwork — Phase 1 plan ("usable planner")

Written 2026-11-23, before any Phase 1 code. Scope is PRD v1.1 Phase 1: **P0-1** backward scheduler, **P0-7** budget and
vendor book, **P0-2** two-peer ownership. The gate is the PRD's: fixtures pass and the demo story passes. Phase 2 does
not start in this run.

## 1. Data model (`prisma/schema/knotwork.prisma`, clone-owned)

Every table has `orgId` (RLS policy, export entry, harness row). One wedding per org (D-07). Money is integer cents.
**No table has a deadline column**: the only stored deadline is `Wedding.date`.

| Table | Holds | Notes |
|---|---|---|
| `Wedding` | title, `date` (the anchor), `timeZone`, `spendThresholdCents`, `consentExpiryDays`, `chaseBufferDays` | `orgId` unique. The three settings change only through a consent request (D-12) |
| `Task` | title, `kind` (template, manual, payment, rsvp), `leadDays`, `bufferDays`, status, assignee, `completedOn`, optional vendor, optional `key` | dates are derived, never stored (D-09). CHECK: lead and buffer are not negative |
| `TaskDependency` | task, depends-on | unique pair; CHECK: not itself. Cycles are refused by the engine before any write |
| `ScheduleBaseline` | one row per committed date (initial or move): from, to, per-task before and after, fingerprint, the request that approved it | history, a record of fact. CHECK: a move names its request |
| `BudgetCategory` | name, `estimateCents` | unique name per org |
| `Expense` | category, optional vendor, description, `amountCents`, `paidOn`, the request that approved it when over the threshold | actuals |
| `BudgetSnapshot` | note, frozen totals (JSON), who, when | PRD "snapshots" |
| `Vendor` | contact, category, status (considering, booked, dropped), scope (`deliverables`, `arriveMin`, `departMin`, `countEstimate`), `countDueDaysBefore`, `onSite`, contract total, `contractSignedOn`, the requests that booked and signed | CHECK: booked needs a booking request; signed needs a signing request |
| `VendorPayment` | label, amount, `dueDaysBefore`, its task, `paidOn`, its expense | a payment is a scheduled task (P0-1) |
| `VendorFlag` | vendor, reason (date moved, scope changed), before and after, raised by and when, acknowledged by and when, note | open while `ackAt` is null |
| `VendorBrief` | vendor, version, body, inputs hash, who, when | regenerable artifact; a new version only when the inputs changed |
| `ConsentRequest` | kind, status, payload (JSON), summary, proposer, `expiresAt`, decider, `decidedAt`, `executedAt`, decline reason | CHECK: approved needs a decider who is not the proposer and an execution time |
| `HelperGrant` | member, scope | unique (org, user, scope) (D-08) |

Migrations (hand-written, D-04): `20261123000000_drop_billing`, `20261123000001_knotwork_phase1`,
`20261123000002_rls_policies_knotwork` (generated by `npm run rls:policies`).

Rules between them: the pure files import nothing from `@/core`, Prisma or Next (a test scans their imports). Routes
call stores; stores call pure functions. `execute.ts` is the only file allowed to set `Wedding.date` after creation,
`Vendor.status = booked`, `Vendor.contractSignedOn`, the three wedding settings, or an over-threshold `Expense`.

### The scheduler, exactly

- A task finishes no later than `due = wedding - bufferDays`, and no later than the start-by date of every unfinished
  task that depends on it. `startBy = due - leadDays`. This is the backward pass.
- Forward from today: `earliestStart = max(today, earliest finish of each unfinished dependency)`. `slack = startBy -
  earliestStart`.
- State (D-09): **done**; **late** if `due < today`; **impossible** if not late and `slack < 0` ("lead time exceeds
  runway"); otherwise **ok**.
- Critical path (D-21): for each unfinished task, `need = leadDays + max(bufferDays, need of each unfinished dependent)`;
  the path starts at the largest `need` (ties: smaller id) and follows the dependent that set it. `runwayDays` is that
  largest `need`: the fewest days before the wedding the plan can start.
- `previewMove(to)` returns what shifts (every unfinished task, old and new dates), what is now late, what is now
  impossible (each marked new or already so), the critical path and a 16-hex fingerprint of all of it.
- `commitMove` runs in one transaction: lock the wedding row, recompute the preview, refuse if the fingerprint differs
  from the one the approver saw, set the date, write the baseline, log the change, raise a flag on every booked vendor.

### The consent machine, exactly

States: `pending` → `approved` (executed in the same transaction) | `declined` | `withdrawn` | `expired`. Only a
partner (an `owner`) proposes. Only a *different* partner approves or declines. Only the proposer withdraws. Any
transition on a request past `expiresAt` turns it `expired` and is refused. Terminal states never change. If execution
refuses (the vendor is gone, the plan changed), the approval is refused whole and the request stays pending.

Designated kinds in Phase 1: `book_vendor`, `sign_contract`, `spend` (amount strictly over the threshold),
`change_date`, `change_settings`. `remove_guest` is in the enum with no surface until Phase 2.

## 4. Oracles (`tools/`, Python standard library only)

## 6. Demo story for the gate (`e2e/knotwork.spec.ts`)

Seed: one synthetic couple, Juniper and Rowan (both owners), one helper, a wedding about eleven months out, the default
template, a venue and a caterer already booked, a florist being considered.

1. Juniper opens the schedule, enters a date six weeks later, and sees the preview: every open task shifts 42 days,
   nothing late, nothing impossible. She proposes the move. The date has not changed.
2. Rowan opens Approvals, sees the same preview, approves. The date is now six weeks later; the schedule shows the new
   dates; both booked vendors show "needs re-confirmation".
3. Juniper adds a florist deposit over the threshold. It does not appear in the budget; a request does. Rowan approves;
   the budget's actual goes up by exactly that amount.
4. Juniper changes the caterer's count estimate. The caterer gets a re-confirmation flag; it shows on the dashboard and
   in the flags list, and clears when acknowledged.
5. The activity feed lists each of those with who and before/after.

## 7. Out of Phase 1

- Everything in P0-3 to P0-6 and all P1 items. No guest-facing surface exists yet.
- Contract **attachments** (D-17) and any upload.
- Brief content fed by the guest engine: headcounts, dietary rollups, the do-not-play list. The brief shows the vendor's
  own scope, payments, linked tasks and open flags, and says which sections arrive in Phase 2.
- Sending anything: no email or SMS is enqueued in Phase 1. Vendors do not get links.
- PDF output, design work beyond plain HTML, and the P1-7 progress dashboard (the home page shows four counts only).
- Editing or deleting an expense, deleting a vendor or a category, and reordering. Corrections are new rows.

## 8. Risks

- The sandbox cannot run Prisma's schema engine (D-04): the migration is hand-written and CI's `migrate diff` is the proof.
- The template's action harness drives every server action with generated input; an action whose schema it cannot
  fill, or that answers before checking a foreign id, fails INV-02/04. Each action checks its refs first.
- Dates: the engine works in whole days and takes "today" as an argument; the only time-zone code is `todayIn`.
